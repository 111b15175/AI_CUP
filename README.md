## 快速上手

第一次提交，照以下步驟做即可。每一步的細節見括號內的章節。

1. **準備工具**：把 `make_submission.py` 與 `test_images.csv` 放在同一個資料夾（kit 解壓縮後就是如此）。只需要 Python 3，不需要安裝其他套件，也不需要連網（第 10.1 節）。
2. **產生範本**：執行 `python make_submission.py --template my_submission.json`。會得到涵蓋全部 1,392 張測試影像的範本，每張影像先填空陣列 `[]`。依環境不同，指令可能是 `python3` 或 `py`。
3. **填入預測**：測試影像在先前發布的資料集中（`test/EO/image/`、`test/IR/image/`）。依第 3 節的格式，把每張影像的預測物件填進對應的陣列：每個物件有 `label`（`solar_panel`、`hotspot`、`crack`）與 `points`；`hotspot`、`crack` 另外填 `reason`（以中文撰寫的根因說明）。框的範圍依第 4 節的標註慣例：異常也是框整個模組。
4. **存檔**：存成 UTF-8、不含 BOM 的標準 JSON（第 3.2 節）。用 Python 可以這樣寫（`submission` 是以影像路徑為 key 的 dict）：

   ```python
   import json
   with open("my_submission.json", "w", encoding="utf-8") as f:  # 不要用 "utf-8-sig"（會加上 BOM）
       json.dump(submission, f, allow_nan=False)                  # 資料混入 NaN 時當場報錯
   ```

   - 座標如果是 numpy 的 `float32`、`int64` 等型別，`json.dump` 會報錯。請先用 `float()` 或陣列的 `.tolist()` 轉成 Python 數值。
   - 加上 `allow_nan=False` 後，資料混入 NaN 時會當場報錯，不會寫出會被退件的 `NaN`。報錯時檔案可能只寫了一部分，請修正資料後重新存檔，再做第 5 步的檢查。
5. **檢查格式**：執行 `python make_submission.py --check my_submission.json`。看到「格式檢查通過」（結束碼 0）再上傳；看到「格式有問題」時，依訊息修正後再檢查一次（第 9.1、10.1 節）。
6. **上傳**：把檢查通過的 JSON 檔上傳到 AIdea 平台。評分程式不讀檔名，直接把收到的檔案內容當成 UTF-8 JSON 讀取。上傳頁面對檔名或檔案類型的其他要求，以 AIdea 上傳頁面與主辦單位公告為準。
7. **看分數**：排行榜明細有五個欄位（第 8 節）。分數不如預期時，先看第 11 節常見問題（例如 Q3、Q9、Q20）。

> **提醒**：`sample_submission.json` 與第 3.1 節的範例只示範欄位格式。框刻意放在影像中沒有模組的位置，直接上傳的分數為 0。請不要把範例當作預測結果提交，請從第 2 步產生的範本開始填寫。

## 名詞解釋

本文件使用的名詞意思如下。名詞欄括號內是對應的英文，方便搜尋。

| 名詞 | 意思 | 詳見 |
|---|---|---|
| EO／IR | EO 是可見光影像（競賽規則頁稱為 RGB），IR 是熱紅外線影像（thermal infrared）。同名的 EO 與 IR 影像在評分時是兩張各自獨立的影像。 | 第 4 節、Q12 |
| key | 提交檔最外層物件的鍵，也就是測試影像的路徑字串（`test_images.csv` 中的一筆）。 | 第 3.1 節 |
| 預測物件、框（prediction、box） | 預測物件是提交檔中描述一個區域的物件（`label`、`points`，異常另有 `reason`）。本文件把預測物件的多邊形（包括 2 點矩形）統稱為「框」。第 5、6 節中簡稱「預測」（第 5 節的公式記作 p），第 3.2、9.1 節的上限中簡稱「物件」，指的都是同一個東西。 | 第 3.1 節 |
| 模組（module） | 一片太陽能模組。標準答案以整個模組為範圍標註，異常也一樣。 | 第 4 節 |
| 異常（anomaly） | `hotspot` 與 `crack` 兩個類別。`solar_panel` 是正常模組。 | 第 3.1、4 節 |
| GT／標準答案（ground truth） | 標準答案是測試集的標註，不公開。本文件把標準答案中的每個標註物件稱為 GT。 | 第 2、5 節 |
| subset（Public／Private） | 計分時使用的測試影像清單。Public 與 Private 各自依自己的清單、用同一套公式計分；清單以外的影像不影響該 subset 的分數。本文件不提供這兩份清單，請對 `test_images.csv` 的全部影像作答（快速上手第 2 步產生的範本已涵蓋全部影像）。 | 第 5、8 節 |
| 重疊（overlap） | 交集面積大於 0。只有邊或頂點相接不算重疊。 | 第 5 節 |
| IoU | 交集面積 ÷ 聯集面積，介於 0～1。 | 第 5 節 |
| TIoU、F1_TIoU | 定位分數。依框與 GT 的重疊程度給部分分數；三個類別各算一個 F1_c（排行榜的 `TIoU_solar_panel`、`TIoU_hotspot`、`TIoU_crack`），再對有 GT 或有預測的類別取平均，得到 F1_TIoU。 | 第 5 節 |
| r(g)、s(p)（recall score、precision score） | 第 5 節定位分數中，每個 GT 的 recall 分數 r(g) 與每個框的 precision 分數 s(p)。s(p) 和根因文字的單句分數 s 是不同的量。 | 第 5 節 |
| 無效多邊形（invalid polygon） | 轉成多邊形後面積為 0 的框（例如所有點共線）。不退件、不得分，但計入定位分數的分母。 | 第 3.1 節 |
| 配對（matching） | 決定哪些框的 `reason` 會被計分：同一張影像、同一類別、IoU ≥ 0.5，一對一。只有異常參與配對。 | 第 6 節 |
| 成因類別（root-cause category） | 每個異常 GT 所屬的根因分組，也是 F1_TEXT 的彙整單位。名稱與數量都不公開。 | 第 7.1 節 |
| 參考描述（reference descriptions） | 每個成因類別都有多個繁體中文的參考描述，評分時拿來與 `reason` 比較。不公開。 | 第 7.1 節 |
| BERTScore | 以 BERT 模型比較兩個句子語意相似度的指標。本競賽採用 rescale 後的 F1，可能是負值；單句不設門檻，也不截斷。 | 第 7.3 節、Q27 |
| 單句分數 s（per-sentence score） | 每個配對成功的 GT 有一個 s：配對到的框的 `reason`，與該 GT 所屬成因類別每個參考描述的 BERTScore F1 取最高值。`reason` 空白時 s = 0。 | 第 7.2 節 |
| raw、F1_TEXT | raw 是各成因類別平均 s 的調和平均（harmonic mean）。任一成因類別完全沒有配對成功的 GT，或任一成因類別的平均 s ≤ 0 時，raw = 0。F1_TEXT 是把 raw 線性換算到 0～1 的根因文字分數（raw ≤ 0.30 時為 0）。 | 第 7.5 節 |
| score（總分，total score） | 0.7 × F1_TIoU + 0.3 × F1_TEXT。 | 第 8 節 |
| 退件（rejection） | 整份提交在讀取或格式檢查階段被拒收，不產生分數（不是以 0 分計算）。 | 第 9.1 節 |

## 3. 提交格式

### 3.1 檔案結構

提交檔是單一 JSON 檔。最外層是一個物件：**key 是測試影像路徑，值是該影像的預測物件陣列**。

```json
{
  "test/EO/image/test_164.jpg": [
    {"label": "solar_panel", "points": [[470.0, 200.0], [730.0, 200.0], [730.0, 620.0], [470.0, 620.0]]},
    {"label": "crack", "points": [[740.0, 200.0], [1000.0, 200.0], [1000.0, 620.0], [740.0, 620.0]],
     "reason": "（示範文字）請填入該模組的異常成因說明。"}
  ],
  "test/IR/image/test_164.jpg": [
    {"label": "solar_panel", "points": [[140.0, 120.0], [250.0, 300.0]]},
    {"label": "hotspot", "points": [[265.0, 120.0], [375.0, 120.0], [375.0, 300.0], [265.0, 300.0]],
     "reason": "（示範文字）請填入該模組的異常成因說明。"}
  ],
  "test/IR/image/test_101.jpg": []
}
```

上例的 key 是真實的測試影像路徑，但座標與文字只用來示範欄位格式：框刻意放在影像中沒有模組的位置，直接上傳的分數為 0。實際提交時，請用 `make_submission.py --template` 產生涵蓋全部測試影像的範本。

| 欄位 | 說明 |
|---|---|
| key | 測試影像路徑，必須與 `test_images.csv` 中的字串**完全一致**，例如 `test/EO/image/test_001.jpg`。斜線方向、大小寫、副檔名都要相同，前面不可加 `./`、`/` 或其他資料夾名稱。 |
| `label` | `solar_panel`、`hotspot`、`crack` 三者之一，全小寫。 |
| `points` | 多邊形頂點 `[x, y]` 的陣列，2～100 個點。像素座標，原點在影像左上角。座標必須是 JSON 數值（整數或小數都可以）。 |
| `reason` | 根因說明文字，單一字串。`hotspot` 與 `crack` 應填寫：缺漏或 `null` 不會退件，但配對成功時單句分數記 0（第 7.2 節）。`solar_panel` 不需要，填了也不會被讀取。 |

補充說明：

- **points 的解讀方式**（標準答案的 `points` 也以同樣的規則轉成多邊形）
  - 只給 2 個點時，視為以這兩點為對角的軸對齊矩形（兩點的先後順序不影響），因此 labelme 的 rectangle（2 點）可以直接送出。
  - 3 個點以上時，依陣列順序連成多邊形。順時針或逆時針都可以，不需要重複第一個點（重複也沒關係）。
  - Python 套件 shapely 判定為不合法（`is_valid` 為否）的多邊形，例如邊互相交錯的 8 字形，會先以 shapely 的 `buffer(0)` 自動修復，修復後可能只剩一部分面積。以 `[[0,0],[10,10],[10,0],[0,10]]` 為例，修復後只剩其中一個三角形（面積 25）。請送出邊不交錯的簡單多邊形。
  - 經過上述轉換（含修復）後面積為 0 的多邊形（例如所有點共線、2 個點的 x 或 y 相同）稱為「無效多邊形」。格式檢查會通過，但這個預測不會得分，仍計入定位分數的分母（第 5 節），也不會參與根因文字的配對（第 6 節）。
  - 座標不會被裁切到影像範圍內，超出影像的部分仍算在多邊形面積裡。
- **其他欄位會被忽略**：評分只讀 `label`、`points`、`reason`。labelme 的 `shape_type`、`group_id`，或自行加的 `score`、`confidence` 等欄位不會造成退件，也不會被讀取。
- **沒有 confidence 欄位**：所有送出的框都會納入定位分數，每個框都計入定位分數的分母（第 5 節）。根因文字分數只看與標準答案配對成功的框（第 6、7 節），沒有配對成功的框不影響根因文字分數。輸出門檻請自行決定。
- **未列出的影像**視為沒有任何偵測結果。沒有偵測結果的影像也可以寫空陣列 `[]`，兩者在評分上沒有差別。
- **reason 只讀全小寫的 `reason` 欄位**。寫在 `root_cause`、`Reason` 等其他欄位名稱下的文字不會被讀取，該筆視同沒有填寫（配對成功時單句分數記 0，見第 7.2 節）。

## 4. 標註慣例

訓練資料與測試集的標準答案，都依照以下三點標註慣例：

- **異常以整個模組為範圍**：`hotspot` 與 `crack` 跟 `solar_panel` 一樣，框的是整個模組，不是模組內的局部區域。
- **同一個模組原則上只標一個類別**：異常模組標成 `hotspot` 或 `crack`，不會再另外標一個 `solar_panel`。
- **`hotspot` 只出現在 IR 影像，`crack` 只出現在 EO 影像。** 評分程式本身不檢查影像類型；EO 與 IR 的同名影像在評分時是兩張各自獨立的影像，不會跨影像配對。

對提交的影響：

- **只框出模組內的局部區域**：與標準答案的 IoU 通常達不到 0.5，因此不會配對。這個框的 `reason` 不會被計分，對應的 GT 也沒有配對成功（若某個成因類別在該 subset 中完全沒有配對成功的 GT，F1_TEXT 為 0，見第 6、7.5 節）。在定位分數中，這個框與該 GT 也只能拿到部分分數。
- **把異常模組標成 `solar_panel`**：類別不同，一定不會配對，該 GT 在根因文字分數中沒有配對成功。這個框在 `solar_panel` 類別通常也拿不到分數。
- **在同一個模組上同時送 `solar_panel` 和異常框**：多出來的 `solar_panel` 框會計入 `solar_panel` 的分母，拉低該類別的分數。

`sample_submission.json` 與 `make_submission.py` 說明中的座標與文字只示範欄位格式，不是標註範例。

## 5. 定位分數 F1_TIoU

定位分數對 `solar_panel`、`hotspot`、`crack` **三個類別分別計算**，再取平均（第 5 步）。計算時只看同一張影像、同一類別的標準答案（以下稱 GT）與預測。不同類別的框不會互相比對。框與同類別 GT 重疊得越完整，分數越高；沒有與任何同類別 GT 重疊的框、被判為重複的框，都記 0 分但仍計入分母。

- 只有該 subset（Public 或 Private）影像清單內的影像會計入；提交檔中其他影像的預測不影響這個 subset 的分數。
- 多邊形的面積、交集與聯集以 Python 套件 shapely（2.x 版）計算。IoU 指「交集面積 ÷ 聯集面積」，聯集面積 = 兩者面積相加 − 交集面積。
- 以下所說的「重疊」指交集面積大於 0；只有邊或頂點相接不算重疊。無效多邊形（第 3.1 節）不與任何物件重疊。
- 「提交檔中較前面」指在同一張影像、同一類別的預測中，在陣列裡的先後順序；「標準答案中較前面」同理。

對每個類別 c，在每張影像中：

1. **每個 GT 的 recall 分數 r(g)**：在同一張影像、類別 c 的預測中，找出與 g **交集面積最大**的預測 p（不是 IoU 最大；交集面積相同時，取提交檔中較前面的預測），
   r(g) = IoU(g, p) × （交集面積 ÷ g 的面積）。
   沒有任何預測與 g 重疊時，r(g) = 0。
   r(g) 與第 3 步的重複判定無關：在第 3 步被改記 0 的預測，仍然可以是某個 GT 的 p。
2. **每個預測的 precision 分數 s(p)**：在同一張影像、類別 c 的 GT 中，找出與 p **交集面積最大**的 GT g（交集面積相同時，取標準答案中較前面的 GT），
   s(p) = IoU(p, g) × (1 − o)，
   其中 o =（p 落在**同類別其他 GT** 內、但不在 g 內的面積）÷ p 的面積。p 同時落在好幾個其他 GT 內時，這些部分取聯集，重疊的地方只算一次。
   p 沒有與任何 GT 重疊時，s(p) = 0。
3. **重複偵測**：如果有多個預測在第 2 步找到的是同一個 GT，只保留 s(p) 最高的那一個（同分時保留提交檔中較前面的那一個），其餘的 s(p) 改記 0，但仍然計入分母。
4. **彙整**（分母是整個 subset 的總數，不是逐張影像平均）：
   - R_c = Σ r(g) ÷（該 subset 中類別 c 的 GT 總數）
   - P_c = Σ s(p) ÷（該 subset 中類別 c 的預測總數，**包含無效多邊形與被判為重複的預測**）
   - F1_c = 2 × R_c × P_c ÷ (R_c + P_c)；R_c + P_c = 0 時為 0。
   - GT 總數為 0 時 R_c = 0；預測總數為 0 時 P_c = 0。
5. **F1_TIoU** = 對「在該 subset 中有 GT 或有預測」的類別取 F1_c 的算術平均。
   - 某類別在該 subset 中既沒有 GT 也沒有預測時，不列入平均。
   - 某類別沒有 GT 但有預測，或有 GT 但沒有預測時，該類別 F1_c = 0，並列入平均。
   - 這裡的「有預測」也包括無效多邊形：例如某 subset 中沒有某類別的 GT，而提交檔在該 subset 的影像中只送了一個該類別的無效多邊形，該類別仍以 F1_c = 0 列入平均。
   - 三個類別都不列入時（該 subset 中沒有任何 GT 與預測），F1_TIoU = 0。

r(g)、s(p)、F1_c 與 F1_TIoU 都介於 0～1。

### 小算例

一張影像、`crack` 類別，有 2 個 GT 與 3 個預測（座標為矩形的左上角與右下角；預測在提交檔中依 P1、P2、P3 的順序排列）：

| 物件 | 範圍 | 面積 |
|---|---|---|
| GT A | (0, 0)～(10, 10) | 100 |
| GT B | (20, 0)～(30, 10) | 100 |
| 預測 P1 | (0, 0)～(10, 8) | 80 |
| 預測 P2 | (0, 0)～(10, 5) | 50 |
| 預測 P3 | (5, 0)～(30, 10) | 250 |

**recall**
- A：與 A 交集最大的預測是 P1（交集 80；P2、P3 都只有 50）。IoU = 80 ÷ 100 = 0.8，交集佔 A 的比例 = 0.8，r(A) = 0.8 × 0.8 = **0.64**。
- B：只有 P3 與 B 重疊，交集 100、聯集 250，IoU = 0.4，交集佔 B 的比例 = 1，r(B) = **0.4**。

**precision**
- P1：交集最大的 GT 是 A，IoU = 0.8，沒有落在其他 GT 的部分，s = **0.8**。
- P2：交集最大的 GT 是 A，IoU = 50 ÷ 100 = 0.5，s = 0.5；但 P1、P2 對應到同一個 GT A，只保留較高的 P1，P2 改記 **0**。
- P3：與 B 交集 100、與 A 交集 50，所以對應 B。IoU = 100 ÷ 250 = 0.4；P3 落在 A 的面積 50，佔 P3 的 50 ÷ 250 = 0.2，s = 0.4 × (1 − 0.2) = **0.32**。

**彙整**
- R = (0.64 + 0.4) ÷ 2 = 0.52
- P = (0.8 + 0 + 0.32) ÷ 3 ≈ 0.3733
- F1_crack = 2 × 0.52 × 0.3733 ÷ (0.52 + 0.3733) ≈ **0.4346**

如果再多送一個無效多邊形（例如三點共線），P 變成 1.12 ÷ 4 = 0.28，F1_crack 降為 0.364。

## 6. 實例配對（根因文字用）

根因文字只對與預測「配對成功」的 GT 計分（第 7 節）。簡單說：同一張影像、同一類別、IoU ≥ 0.5，而且一對一。詳細規則如下：

- 同一張影像中，**同一類別**才會配對：`hotspot` 只與 `hotspot`、`crack` 只與 `crack` 配對。
- `solar_panel` 不參與配對（但 `solar_panel` 的框照樣計入定位分數）。
- 兩者多邊形的 **IoU ≥ 0.5**（剛好 0.5 也算）。IoU 的算法與第 5 節相同。
- **一對一，依 IoU 由大到小貪婪配對**：在同一張影像、同一類別中，列出所有 IoU ≥ 0.5 的（GT, 預測）組合，依 IoU 由大到小排序；IoU 相同時，先依 GT 在標準答案中的先後、再依預測在提交檔中的先後排序（都是指同一張影像、同一類別內的順序）。依這個順序逐一檢查：GT 與預測都還沒配對過，才配對成功；其中任一個已經配對過，就跳過這個組合。
  - 因此每個 GT、每個預測都最多只配對一次。同一個 GT 上有多個 IoU ≥ 0.5 的框時，最多只有其中一個會配對，通常是 IoU 最高的那一個（IoU 相同時是提交檔中較前面的那一個）。但如果那個框已經先配給另一個 GT（例如一個框剛好涵蓋兩個相鄰模組），就依上述順序改由下一個框配對。評分採用的是實際配對到的框的 `reason`。兩個完全相同的框，最多只有一個會配對到。
  - 一個框跨過多個模組時，與每個模組的 IoU 都會偏低（剛好涵蓋 n 個同樣大小的相鄰模組時，與每個模組的 IoU 最多只有 1/n），通常一個都配對不到；即使配對到，也只會配對其中一個。
- 配對只看 `label` 與 `points`，與 `reason` 的內容無關；無效多邊形不會配對。
- 最後沒有配對成功的預測（IoU 不到 0.5、重複框、框在沒有該類別 GT 的位置等）對根因文字分數沒有任何影響，但照樣計入定位分數（第 5 節）。

注意：配對與第 5 節的 TIoU 是兩套不同的計算。TIoU 會依重疊程度給部分分數，因此 **TIoU 大於 0 不代表已經有預測配對成功**。例如 IoU 只有 0.3 的框可以拿到 TIoU 的部分分數，但不會配對，它的 `reason` 也就不會被計分。

## 7. 根因文字分數 F1_TEXT

F1_TEXT 只看配對成功的 GT。計算分四步：先算每個配對成功 GT 的單句分數 s（7.2 節），在每個成因類別內平均，再對各成因類別取調和平均得到 raw，最後把 raw 線性換算到 0～1（7.5 節）。以下任一情況，F1_TEXT 都是 0：某個成因類別在該 subset 中完全沒有配對成功的 GT、某個成因類別的平均 s ≤ 0、調和平均 raw ≤ 0.30（7.5 節、Q9）。

### 7.1 成因類別與參考描述

標準答案中，每個 `hotspot`／`crack` 物件都屬於一個「成因類別」。每個成因類別有多個繁體中文的參考描述（即競賽規則所稱的「多個參考根因描述」）；同一個成因類別的 GT 共用同一組參考描述。成因類別的名稱、數量與參考描述都不公開。

成因類別也是根因文字分數的彙整單位：先在每個成因類別內平均，再對各成因類別取調和平均（7.5 節）。

### 7.2 單句分數 s

對每個**配對成功**的 GT，計算一個單句分數 s：

1. 取配對到的預測的 `reason`。如果 `reason` 缺漏、為 `null`，或以 Python 的 `str.strip()` 去除前後空白後是空字串，視為**空白**：s = **0**，不送進 BERTScore。
2. 否則，以去除前後空白後的 `reason`，用 BERTScore 與該 GT 所屬成因類別的**每一個**參考描述分別比較，取 F1 的**最高值**作為 s（設定見 7.3 節）。
3. BERTScore 算出的值如果不是有限的數值（例如 NaN），s 記為 0。

s 不做任何截斷或換算：

- 與某個參考描述一字不差的句子，s 約等於 1。
- s 可能是**負值**（rescale 的關係，見 7.3 節），負值會原樣計入 7.5 節的平均。
- 沒有配對成功的 GT 沒有 s（不是記 0），不計入 7.5 節的平均。

「空白」的精確定義是 `reason.strip()` 為空字串。`str.strip()` 去除的是 Python 認定的空白字元（`str.isspace()` 為真的字元），包括半形空白、全形空白（U+3000）、換行、Tab、不換行空白（U+00A0）等：

| `reason` 的內容 | 視為空白？ | 結果 |
|---|---|---|
| 缺漏（沒有 `reason` 欄位）、`null`、空字串 `""` | 是 | s = 0 |
| 只有半形空白、全形空白、換行、Tab 等空白字元 | 是 | s = 0 |
| 只有零寬字元（或零寬字元夾雜空白字元），例如零寬空白 U+200B、U+200C、U+200D、U+FEFF | **否** | `str.strip()` 不會去除零寬字元，因此會送進 BERTScore。這類字元在 BERT 斷詞時會被濾掉，等於一個空句，BERTScore 的原始值記為 0，rescale 後 s ≈ **−1.21**（用 `bert_score` 試算時會印出 `Warning: Empty candidate sentence detected; ...`） |
| 只有標點符號，例如「。」 | 否 | 照常計算 BERTScore，s 通常是負值 |

### 7.3 BERTScore 設定

| 項目 | 設定 |
|---|---|
| 套件 | `bert_score`（PyPI 套件名稱 `bert-score`） |
| 模型 | `bert-base-chinese`（平台使用此模型的離線檔案） |
| 語言 | `lang="zh"` |
| 使用的層 | 第 8 層的輸出（`num_layers=8`，即 `bert_score` 對此模型的預設值） |
| IDF 加權 | 不使用（`idf=False`，即預設值） |
| rescale | 使用 `bert_score` 套件內建的 `bert-base-chinese` 中文 baseline（`rescale_baseline/zh/bert-base-chinese.tsv`，`rescale_with_baseline=True`） |
| 採用的分數 | F1 |
| 多個參考描述 | 與每個參考描述分別比較，取最高的 F1（即 7.2 節的 s） |
| 前處理 | 評分程式本身只用 `str.strip()` 去除 `reason` 前後的空白，不做繁簡轉換、不刪除標點，也不做其他修改（斷詞由模型的 tokenizer 處理） |

rescale 的計算方式為 F′ = (F − b) ÷ (1 − b)，b 是 baseline 檔中第 8 層的 F 值（約 0.5476）。因此與參考描述的相似度低於 baseline 的句子，s 會是**負值**；斷詞後是空句的 `reason`（例如只有零寬字元），s = −b ÷ (1 − b) ≈ −1.21。

想自己試算某個句子的 s，可以用以下程式（`refs` 換成你自己準備的參考描述）。需要先安裝 `bert-score`、`transformers`、`torch`（`pip install bert-score transformers torch`）。第一次執行時會從 Hugging Face 下載 `bert-base-chinese` 模型（數百 MB），需要連網；之後會使用電腦上的快取。CPU 即可執行。

```python
import math
from bert_score import BERTScorer

# 與平台相同的設定：bert-base-chinese、第 8 層、中文、以內建 baseline rescale、不用 IDF
scorer = BERTScorer(model_type="bert-base-chinese", num_layers=8, lang="zh",
                    rescale_with_baseline=True)

def single_score(reason, refs):
    """reason：預測的根因文字；refs：該成因類別的參考描述（字串的 list）。"""
    if not isinstance(reason, str) or not reason.strip():
        return 0.0                              # 空白：s = 0，不送進 BERTScore（7.2 節）
    P, R, F = scorer.score([reason.strip()], [refs])
    s = F.item()                                # 與每個參考描述比較後取最高的 F1
    return s if math.isfinite(s) else 0.0

print(single_score("你的根因描述", ["參考描述一", "參考描述二", "參考描述三"]))
```

- `model_type` 請寫成 `"bert-base-chinese"`、`lang` 為 `"zh"`：此時 `bert_score` 會自動使用套件內建的 `rescale_baseline/zh/bert-base-chinese.tsv`，與平台使用的 baseline 檔相同，不需要另外指定 `baseline_path`。改用其他寫法的模型名稱時，`bert_score` 可能找不到這個 baseline 檔。
- 平台以同一個模型的離線檔案評分，模型、層數、baseline 與其他設定都與上面的程式相同。
- 本範例在 Python 3.13、bert-score 0.3.12、transformers 4.57.6、torch 2.14.0（CPU）上測試過。不同的硬體、套件版本或批次組合，可能讓結果在小數點後第 6 位以後有極小的差異。
- 執行時若出現 torch 的 `UserWarning: The given NumPy array is not writable`，可以忽略，不影響結果。

### 7.4 使用語言

- **請以中文撰寫，建議使用繁體中文。** 參考描述是繁體中文，評分使用中文 BERT 模型。
- 評分程式不會做繁簡轉換或翻譯。簡體中文不會被退件，但 s 通常會略低於同樣內容的繁體中文。
- 英文等非中文的句子不會被退件，但 s 通常接近 0 甚至是負值。只要某個成因類別的平均 s ≤ 0，F1_TEXT 就是 0；平均略大於 0 時，調和平均 raw 也要大於 0.30，F1_TEXT 才會大於 0（7.5 節）。

### 7.5 彙整方式

F1_TEXT 在每個 subset（Public 或 Private）的影像範圍內各自計算，步驟如下：

1. **G**：該 subset 的標準答案中出現的成因類別集合（由該 subset 內所有 `hotspot`／`crack` GT 決定，不論這些 GT 有沒有被配對）。
2. **各成因類別的平均 m_k**：對 G 中的每個成因類別 k，m_k = 該類別所有**配對成功**的 GT 的 s 的算術平均。
   - `reason` 空白的配對以 s = 0 **計入**平均。
   - 沒有配對成功的 GT **不計入**平均（分子、分母都不算）。
   - 沒有配對成功的預測不影響 m_k。
3. **raw**：
   - G 中任一成因類別沒有任何配對成功的 GT，或任一成因類別的 m_k ≤ 0 → raw = 0。
   - 否則，raw = G 中各成因類別 m_k 的**調和平均** = |G| ÷ Σ (1 ÷ m_k)，|G| 是 G 中的類別數。
4. **F1_TEXT** = min(max((raw − 0.30) ÷ (0.70 − 0.30), 0), 1)，也就是 (raw − 0.30) ÷ 0.40 再限制在 0～1 之間。
5. 該 subset 的標準答案中沒有任何 `hotspot`／`crack` GT 時（G 是空的），F1_TEXT = 0。

| raw | ≤ 0.30 | 0.40 | 0.50 | 0.60 | ≥ 0.70 |
|---|---|---|---|---|---|
| F1_TEXT | 0 | 0.25 | 0.5 | 0.75 | 1 |

- 換算只在最後對 raw 做一次，單句分數 s 不逐句截斷或換算。
- 調和平均受最低的成因類別影響最大：只要有一個成因類別的平均偏低，raw 就會明顯下降。
- Public 與 Private 各自計算，G 也各自依該 subset 的標準答案決定。
- 每個異常 GT 都配對成功、且 `reason` 都與參考描述之一完全相同時，F1_TEXT = 1；空的提交 F1_TEXT = 0。

各種情況對兩項分數的影響整理如下：

| 情況 | 定位分數 F1_TIoU（第 5 節） | 根因文字分數 F1_TEXT |
|---|---|---|
| GT 沒有配對成功（漏檢） | r(g) 依重疊程度給部分分數，完全沒有重疊時為 0；一律計入 R_c 的分母 | 不計入該成因類別的平均；但若某個成因類別在該 subset 中完全沒有配對成功的 GT，F1_TEXT = 0 |
| 重複框（同一個 GT 上有多個框） | 只保留 s(p) 最高的一個，其餘記 0，仍計入 P_c 的分母 | 最多只有一個會配對（通常是 IoU 最高的那一個，見第 6 節），採用它的 `reason`；其餘沒有配對，不影響 F1_TEXT |
| 沒有配對成功的預測（IoU < 0.5、框在沒有該類別 GT 的位置等） | 計入 P_c 的分母 | 不影響 |
| 配對成功但 `reason` 空白 | 不影響 | s = 0，計入該成因類別的平均 |
| 配對成功但 `reason` 只有零寬字元 | 不影響 | 不算空白，照常計分，s ≈ −1.21，計入平均 |
| 無效多邊形 | 不得分，計入分母 | 不會配對，不影響 |

#### 小算例

假設某個 subset 的標準答案中有兩個成因類別 `GROUP_A`、`GROUP_B`（名稱與類別數都是為了說明而假設的，與正式測試集無關）：`GROUP_A` 有 4 個 GT（甲1～甲4），`GROUP_B` 有 2 個 GT（乙1、乙2）。表中的 s 也是假設的數值，只用來說明計算方式。

| GT | 成因類別 | 配對結果 | s |
|---|---|---|---|
| 甲1 | `GROUP_A` | 配對成功 | 0.80 |
| 甲2 | `GROUP_A` | 配對成功 | 0.60 |
| 甲3 | `GROUP_A` | 配對成功，但 `reason` 只有全形空白 | 0（空白） |
| 甲4 | `GROUP_A` | 沒有配對成功（框與它的 IoU 只有 1/3） | 不計入 |
| 乙1 | `GROUP_B` | 配對成功 | 0.70 |
| 乙2 | `GROUP_B` | 配對成功 | 0.50 |

另外還有一個框落在沒有 GT 的位置。它會拉低定位分數，但不影響 F1_TEXT。

**情況一：一般情況**
- m_A = (0.80 + 0.60 + 0) ÷ 3 ≈ 0.466667（甲4 沒有配對成功，不計入）
- m_B = (0.70 + 0.50) ÷ 2 = 0.60
- raw = 2 ÷ (1 ÷ 0.466667 + 1 ÷ 0.60) = 2 ÷ (2.142857 + 1.666667) = 0.525
- F1_TEXT = (0.525 − 0.30) ÷ 0.40 = **0.5625**

**情況二：某個成因類別沒有任何配對成功**
乙1、乙2 的框與 GT 的 IoU 都只有 1/3，沒有配對成功。`GROUP_B` 沒有任何配對成功的 GT → raw = 0，F1_TEXT = **0**（即使 m_A ≈ 0.466667）。

**情況三：某個成因類別的平均 ≤ 0**
乙1、乙2 都配對成功，但 s 分別是 0.10 與 −0.20。m_B = (0.10 − 0.20) ÷ 2 = −0.05 ≤ 0 → raw = 0，F1_TEXT = **0**。

**情況四：調和平均 ≤ 0.30**
乙1、乙2 都配對成功，s 都是 0.20。m_B = 0.20 > 0，raw = 2 ÷ (2.142857 + 5) = 0.28 ≤ 0.30，F1_TEXT = **0**。

## 8. 總分與排行榜明細

```
score = 0.7 × F1_TIoU + 0.3 × F1_TEXT
```

- F1_TIoU、F1_TEXT 都介於 0～1，總分也介於 0～1。
- 總分以**未四捨五入**的 F1_TIoU 與 F1_TEXT 計算，總分本身也不做四捨五入。排行榜明細中的 F1_TIoU、F1_TEXT 是四捨五入到小數點後 6 位的值，所以用明細自己重算總分時，最後幾位可能有些微差異。
- Public 與 Private 各自依其影像清單、用同一套公式計算；只有清單內的影像會被評分。
- 排行榜顯示的明細欄位只有下列五個：

| 欄位 | 意義 |
|---|---|
| `F1_TIoU` | 定位分數（第 5 節） |
| `F1_TEXT` | 根因文字分數（第 7 節） |
| `TIoU_solar_panel` | `solar_panel` 類別的 F1_c |
| `TIoU_hotspot` | `hotspot` 類別的 F1_c |
| `TIoU_crack` | `crack` 類別的 F1_c |

- 明細欄位四捨五入到小數點後 6 位。

## 9. 邊界情況

### 9.1 整份退件的條件

只要符合下列任一條件，整份提交都會被退件、不產生分數（不是以 0 分計算）。`make_submission.py --check` 會檢查同樣的條件。

**讀取階段**

| 條件 | 評分程式的訊息（開頭） |
|---|---|
| 檔案超過 52,428,800 位元組（50 MB） | `prediction file too large` |
| 不是 UTF-8 編碼（例如存成 Big5） | `'utf-8' codec can't decode ...` |
| 檔案開頭有 BOM | `Unexpected UTF-8 BOM` |
| 不是合法 JSON（例如用單引號、最後多一個逗號、加註解） | JSON 解析錯誤訊息 |
| `NaN`、`Infinity`、`-Infinity` 出現在檔案任何位置（包括會被忽略的欄位） | `prediction contains non-finite constant` |
| 其他無法解析的 JSON（例如巢狀層數過深、位數極多的整數） | Python 的例外訊息（例如 `maximum recursion depth exceeded ...`、`Exceeds the limit (4300 digits) ...`） |

**格式檢查（check_data）**

| 回傳碼 | 條件 | 評分程式的訊息（開頭） |
|---|---|---|
| -1 | 最外層不是物件 | `prediction must be a JSON object keyed by image path` |
| -2 | 有 key 不在 `test_images.csv` 中 | `prediction contains N unknown image id(s)` |
| -3 | key 對應的值不是陣列 | `value of '...' must be a list` |
| -4 | 單張影像超過 500 個物件 | `'...' has N objects, exceeds limit 500` |
| -5 | 物件總數超過 400,000 | `total objects exceed limit 400000` |
| -6 | 陣列中的元素不是物件 | `object in '...' must be a dict` |
| -7 | `label` 缺漏，或不是三者之一（大小寫必須相符） | `invalid label ...` |
| -8 | `points` 缺漏、不是陣列，或點數不在 2～100 | `'points' in '...' must be a list of 2~100 vertices` |
| -9 | 頂點不是 `[x, y]` 兩個元素的陣列 | `each vertex in '...' must be [x, y]` |
| -10 | 座標不是數值（字串、`null`、`true`／`false`） | `non-numeric coordinate in '...'` |
| -11 | 座標溢位成無限大（例如 `1e400`） | `non-finite coordinate in '...'` |
| -12 | 座標絕對值超過 1,000,000 | `coordinate out of range in '...'` |
| -13 | `hotspot`／`crack` 的 `reason` 不是字串也不是 `null`（例如陣列、數字） | `'reason' in '...' must be a string` |
| -14 | `hotspot`／`crack` 的 `reason` 超過 500 字元 | `'reason' in '...' exceeds 500 characters` |
| -15 | 檢查過程中發生其他錯誤，例如整數座標大到無法轉成浮點數（像 `1` 後面接 400 個 `0`） | `check_data failed: ...`（上例為 `check_data failed: int too large to convert to float`） |

格式檢查遇到第一個錯誤就停止，並回傳該錯誤的回傳碼。格式檢查通過、但有影像沒列在提交檔中時，回傳碼仍為 0，訊息為 `N image(s) absent from prediction, treated as no detection`，這只是提醒。

表中的回傳碼與英文訊息是平台評分程式的輸出。`make_submission.py --check` 不顯示回傳碼，而是用中文列出問題種類（例如「label 不正確」）、處數與例子，格式檢查階段的各類問題會一次列出。它的結束碼只有 0、1、2（第 10.1 節），和這裡的回傳碼不同。

### 9.2 其他情況

- **reason 空白**：缺漏、`null`、空字串，或只有空白字元（半形空白、全形空白、換行、Tab 等），格式檢查都會通過，不影響定位分數與配對；配對成功時該筆 s 記 0，並計入該成因類別的平均（第 7.2、7.5 節）。
- **reason 只有零寬字元**（例如 U+200B）：不算空白，會照常送進 BERTScore，s ≈ −1.21，並計入該成因類別的平均（第 7.2 節）。
- **reason 寫在其他欄位**：`root_cause`、`Reason` 等欄位不會被讀取，等同沒有填寫。
- **solar_panel 的 reason**：不讀取、也不檢查（即使不是字串也不會退件；但 `NaN`、`Infinity`、`-Infinity` 不論寫在哪裡都會在讀取階段退件，見 9.1 節）；`solar_panel` 的框照樣計入定位分數。
- **同一個 key 在 JSON 中出現兩次**：依 JSON 解析的行為，只有最後一次出現的內容有效，前面的會被覆蓋。請避免重複的 key。
- **無效多邊形**：不退件、不得分，計入定位分數的分母；不會參與配對，因此不影響根因文字分數（第 3.1、5、6 節）。
- **沒有配對成功的預測**：不影響根因文字分數，但仍計入定位分數的分母（第 5、6 節）。
- **F1_TEXT 為 0 的常見原因**：
  - 沒有任何框與異常 GT 配對成功（例如只框局部區域、類別標錯、IoU 不到 0.5）；
  - 某一個成因類別在該 subset 中完全沒有配對成功的 GT；
  - 某一個成因類別的平均 s ≤ 0（例如以英文撰寫，或該類別配對成功的 `reason` 全部空白或寫在其他欄位）；
  - 各成因類別平均的調和平均 raw ≤ 0.30。
- **subset 中沒有異常 GT**：該 subset 的標準答案中沒有任何 `hotspot`／`crack` GT 時，F1_TEXT = 0。
- **空的 subset**：如果某個 subset 的影像清單是空的，該 subset 的分數為 0。

## 10. 本機工具

### 10.1 產生提交範本與檢查格式（make_submission.py）

```
python make_submission.py --template my_submission.json
python make_submission.py --check my_submission.json
```

- 只需要 Python 3 標準函式庫，不需要安裝其他套件，也不需要連網。
- `--template 檔名`：產生涵蓋全部測試影像的空白範本（每張先填空陣列），把預測填進去即可。已存在的檔案不會被覆寫；確定要覆寫請加 `--force`。
- `--check 檔名`：送出前檢查格式，接受／退件的條件與平台評分程式相同（第 9.1 節）。通過只代表格式正確，不代表分數高低。通過時另外會列出幾項提醒（例如有影像未列出、`reason` 空白或只含零寬字元、`reason` 不含中文字、key 重複），提醒不影響通過與否。
- `--test-images 路徑`：兩種用法都需要 `test_images.csv`。未指定時，依序在 `make_submission.py` 所在的資料夾與目前的工作目錄尋找；放在其他位置時用這個參數指定。
- 結束碼：
  - `0`：格式檢查通過（或範本已產生）
  - `1`：格式有問題，平台會退件
  - `2`：無法執行（例如找不到提交檔或 `test_images.csv`、清單內容不正確、範本檔已存在）

> Windows 使用者：如果中文訊息顯示成亂碼，請先設定環境變數 `PYTHONUTF8=1`（命令提示字元：`set PYTHONUTF8=1`；PowerShell：`$env:PYTHONUTF8="1"`）再執行。

### 10.2 試算單句分數

用第 7.3 節的範例程式，可以在自己的電腦上算出某個 `reason` 對一組參考描述的單句分數 s，設定與平台相同。需要安裝 `bert-score`、`transformers`、`torch`，第一次執行需要連網下載模型。

### 10.3 自行建立驗證流程

- 測試集的標準答案不公開。建議用資料集補充檔中的 `train_groups.csv`，以 `group` 為單位從訓練資料切出驗證集。同一個 group 的影格來自同一次連續拍攝、畫面高度相似；請不要把同一個 group 拆到訓練與驗證兩邊，否則驗證分數會偏高。
- 依第 5～7 節自行實作評分，即可在驗證集上計算分數。F1_TIoU 可以完全依本文件計算。
- F1_TEXT 需要成因類別與參考描述。正式評分使用的成因類別與參考描述不公開，自行驗證時只能自行決定分法與參考描述，所以自己算出的 F1_TEXT 只能作為參考，不會等於排行榜分數。

## 11. 常見問題

依主題查找：

- 提交檔與格式：Q1、Q2、Q6、Q8、Q10～Q15
- 框的範圍與類別：Q16～Q18
- 根因文字：Q2、Q3、Q4、Q9、Q19、Q24、Q27、Q28
- 分數與排行榜：Q3、Q5、Q9、Q20～Q25
- 規則與其他：Q7、Q26

**Q1. 提交格式以哪一份為準？**
以本文件第 3 節、`sample_submission.json` 與 `make_submission.py` 檔頭說明中的「提交檔格式」一段為準，三者的欄位格式一致。競賽規則頁「上傳格式說明」中的 `image_id`、`modality`、`predictions`、`polygon`、`root_cause`，以及 Normal／Crack／String Offline／Hot Spot 等名稱不適用（對照見 3.3 節）。

**Q2. 根因文字要放哪個欄位？可以寫很多句嗎？**
放在全小寫的 `reason`，值為單一字串。可以寫多個句子，但要寫在同一個字串裡。
- 長度最多 500 字元（空白、標點、換行也計入，第 3.2 節）。
- 不需要固定句型：評分程式不解析句子結構，只把去除前後空白後的整段字串送進 BERTScore（第 7.2、7.3 節）。整段一起與參考描述比較；加入與成因無關的內容，通常會讓 s 下降。
- 不可寫成陣列（例如 `["句子一", "句子二"]`），否則整份退件（第 9.1 節）。
- 每個預測物件只需要提供一個 `reason`。標準答案端則是每個成因類別有多個參考描述，評分時與每個參考描述分別比較、取最高分（第 7.2、7.3 節）。

**Q3. 我的 TIoU_hotspot 不是 0，為什麼看起來根因文字沒有被計分？**
TIoU 會依重疊程度給部分分數，TIoU 大於 0 不代表有配對成功。根因文字只在同類別、IoU ≥ 0.5、一對一配對成功時才計分；沒有配對成功的框，它的 `reason` 不會被計分。標準答案的異常以整個模組為範圍：只框局部區域通常不會配對，把異常模組標成 `solar_panel` 則一定不會配對（第 4、6 節）。另外，即使有框配對成功，只要該 subset 中有任一成因類別完全沒有配對成功的 GT、任一成因類別的平均 s ≤ 0，或調和平均 raw ≤ 0.30，F1_TEXT 都會是 0（第 7.5 節）。

**Q4. 根因文字要用什麼語言？**
請以中文撰寫，建議繁體中文。英文等非中文不會被退件，但 s 通常接近 0 或為負值。某個成因類別的平均 s ≤ 0 時，F1_TEXT 為 0；即使平均略大於 0，調和平均 raw 也要大於 0.30，F1_TEXT 才會大於 0（第 7.4、7.5 節）。

**Q5. 有沒有 confidence 欄位？**
沒有。所有送出的框都會納入定位分數：多送的框會增加 precision 的分母，被判為重複的框記 0 分但仍計入分母（第 5 節）。根因文字分數只看配對成功的框，沒有配對成功的框不影響文字分數；同一個 GT 上有多個框時，最多只有一個會配對（通常是 IoU 最高的那一個），採用的是它的 `reason`（第 6 節）。請自行決定輸出門檻。

**Q6. 可以只給 2 個點嗎？**
可以。2 個點視為以兩點為對角的軸對齊矩形。需要斜放或不規則形狀時，請給 3 個以上的點（第 3.1 節）。

**Q7. 為什麼 kit 沒有附評分程式？**
本文件完整描述平台評分程式的計算方式（提交格式與退件條件見第 3、9 節，計分方式見第 5～8 節），依本文件即可自行實作出相同的計算。排行榜分數以平台評分程式的計算結果為準；各隊拿到的說明完全相同。

**Q8. 格式錯誤會怎樣？**
整份提交在讀取或格式檢查階段被退件，不會產生分數（第 9.1 節）。送出前請先用 `python make_submission.py --check` 檢查。

**Q9. 為什麼我的 F1_TEXT 是 0？**
常見原因有四種（第 7.5、9.2 節）：
- 沒有任何框與異常 GT 配對成功，例如只框局部區域、類別標錯，或 IoU 不到 0.5（Q3、Q16）；
- 某一個成因類別在該 subset 中完全沒有配對成功的 GT；
- 某一個成因類別的平均 s ≤ 0，例如以英文撰寫，或配對成功的 `reason` 全部沒填、空白，或寫在 `root_cause` 等其他欄位（都視為空白，s = 0，第 3.1、7.2 節）；
- 各成因類別平均的調和平均 raw ≤ 0.30。

排行榜只顯示 F1_TEXT，不顯示各成因類別的明細。

**Q10. `test_images.csv` 是什麼？要放在哪裡？key 要怎麼寫？**
`test_images.csv` 是測試影像的路徑清單，提交檔的 key 必須直接使用其中的字串。
- 它不是影像，也不含任何答案。只有一欄 `filename`，共 1,392 筆（EO、IR 各 696 筆）。
- 放在 `make_submission.py` 所在的資料夾即可；也可以放在目前的工作目錄，或用 `--test-images 路徑` 指定（第 10.1 節）。
- key 一律是 `test/` 開頭的相對路徑，例如 `test/EO/image/test_001.jpg`，與資料集解壓縮到哪個資料夾無關。大小寫、斜線方向、副檔名都要完全相同，前面不可加 `./`、`/` 或其他資料夾名稱。只要有一個 key 不在清單中，整份提交就會退件（第 3.1、9.1 節）。

**Q11. 可以直接上傳 `sample_submission.json` 嗎？**
可以通過格式檢查，但分數為 0，請不要當作預測結果提交。
- `sample_submission.json` 只列出 6 張影像，框刻意放在影像中沒有模組的位置，只用來示範欄位怎麼寫（第 3.1 節）。
- 實際提交請用 `python make_submission.py --template my_submission.json` 產生涵蓋全部測試影像的範本，再填入自己模型的預測（見「快速上手」）。

**Q12. EO 與 IR 影像要怎麼寫？座標可以共用嗎？**
分開寫，座標不共用。
- 同名的 EO 與 IR 影像（例如 `test/EO/image/test_001.jpg` 與 `test/IR/image/test_001.jpg`）是兩個不同的 key，各自有自己的預測物件陣列。
- 兩種影像的解析度與視角不同，不保證像素對齊（詳見資料集說明）。`points` 一律使用該張影像自己的像素座標，不可把 EO 的座標直接套到 IR，反之亦然。
- 評分時，同名的 EO 與 IR 是兩張各自獨立的影像，不會跨影像配對：寫在 EO key 下的框，只會和 EO 影像的 GT 比較（第 4 節）。

**Q13. 沒有偵測到任何東西的影像要怎麼寫？**
寫空陣列 `[]`，或乾脆不列出，兩者評分完全相同。
- `--template` 產生的範本每張影像都是 `[]`，沒有預測的影像保持原樣即可。
- 不列出的影像視為沒有任何偵測結果。格式檢查會提醒有幾張影像未列出，這只是提醒，不會退件（第 3.1、9.1 節）。

**Q14. `label` 可以寫 `Normal`、`Hot Spot` 或大寫嗎？**
不行，整份提交會退件。
- `label` 只能是全小寫的 `solar_panel`、`hotspot`、`crack`。`Normal`、`Hot Spot`、`Hotspot`、`HOTSPOT`、`String Offline` 等寫法都會在格式檢查被退件（`--check` 會顯示「label 不正確」，對應第 9.1 節的回傳碼 -7）。
- 競賽規則頁的類別名稱與實際 `label` 的對照見第 3.3 節。

**Q15. 座標要用整數還是小數？可以超出影像範圍嗎？**
整數或小數都可以。超出影像範圍不會退件，也不會被裁切。
- 座標必須是 JSON 數值，不可寫成字串（例如 `"12.5"`）、`null` 或 `true`／`false`；絕對值不可超過 1,000,000（第 3.2 節）。
- 評分程式不會把座標裁切到影像範圍內，超出影像的部分仍算在多邊形面積裡（第 3.1 節），因此也會影響 IoU。

**Q16. `hotspot`／`crack` 要框整個模組，還是只框瑕疵的位置？**
框整個模組。
- 標準答案的異常以整個模組為範圍，和 `solar_panel` 一樣（第 4 節）。
- 只框模組內的局部區域時，與 GT 的 IoU 通常達不到 0.5，不會配對，這個框的 `reason` 不會被計分；在定位分數中也只能拿到部分分數（第 4、6 節）。

**Q17. 同一個模組可以同時送 `solar_panel` 和 `hotspot`／`crack` 嗎？**
不會退件，但兩個框之中與標準答案類別不同的那一個，會拉低它所屬類別的定位分數。
- 標準答案中，同一個模組原則上只標一個類別：異常模組只標 `hotspot` 或 `crack`，不會再標 `solar_panel`（第 4 節）。
- 定位分數是三個類別各自計算的（第 5 節）。與標準答案類別不同的那個框，在它的類別中沒有對應的 GT：沒有與該類別任何 GT 重疊時，定位的 precision 分數 s(p) = 0（不是根因文字的 s），但仍計入該類別 P_c 的分母，拉低該類別的 F1_c，進而拉低 F1_TIoU。
- 例如：在異常模組上多送的 `solar_panel` 框，會拉低 `TIoU_solar_panel`；在正常模組上多送的 `hotspot` 框，會拉低 `TIoU_hotspot`。

**Q18. 可以在 EO 影像送 `hotspot`、在 IR 影像送 `crack` 嗎？**
不會退件，但這類框不會得分，還會拉低該類別的分數。
- 評分程式不檢查影像類型，只依 `label` 與 `points` 計分（第 4 節）。
- 標準答案中 `hotspot` 只出現在 IR 影像、`crack` 只出現在 EO 影像（第 4 節）。因此 EO 影像中的 `hotspot` 框、IR 影像中的 `crack` 框，在同一張影像中沒有同類別的 GT，定位的 precision 分數 s(p) = 0（不是根因文字的 s），但仍計入該類別 P_c 的分母（第 5 節）。

**Q19. 可以用簡體中文嗎？**
可以，不會退件，但建議使用繁體中文。
- 參考描述是繁體中文。評分程式不做繁簡轉換，簡體中文的 s 通常會略低於同樣內容的繁體中文（第 7.4 節）。
- 英文等非中文的句子同樣不會退件，但 s 通常接近 0 甚至是負值（Q4）。

**Q20. `--check` 通過了，為什麼分數還是很低或是 0？**
`--check` 只檢查格式，不檢查預測內容；通過只代表可以被正常評分，不代表分數高低（第 10.1 節）。分數偏低時，可以依序確認：
- 是否把 `sample_submission.json` 或文件中的範例座標當成預測提交（Q11）；
- 座標是否為該張影像的像素座標（不是 0～1 的比例座標）、原點在左上角（第 3.1 節）。只給 2 個點時，兩點是矩形的兩個對角，不是「左上角加寬高」；
- EO 與 IR 的座標是否寫對影像（Q12）；
- 框的範圍與類別是否符合標註慣例：異常也框整個模組、同一個模組只送一個類別（第 4 節、Q16、Q17）；
- F1_TEXT 為 0 的常見原因見 Q9；TIoU 大於 0 但根因文字沒有計分見 Q3。

**Q21. Public 與 Private 怎麼計分？最終排名看哪一次提交？**
兩者用同一套公式計分。最終排名以 Private 的成績為主要依據，採截止前**最後一次**有效提交，並配合程式碼及技術文件審查確認。
- 計分：Public 與 Private 各自依其影像清單、用同一套公式計算，只有清單內的影像會被評分（第 8 節）。
- Public Leaderboard：每支隊伍每一日曆日最多上傳 3 次。排行榜保留各隊自競賽開始至當下所有有效提交中的最高分，並依該分數排名。Public 分數僅供競賽期間參考，不納入最終排名。
- Private Leaderboard：預計於 2026/12/01 10:00:00 至 2026/12/04 23:59:59（臺灣時間，UTC+8）開放提交，每一日曆日最多上傳 3 次。最終排名以截止時間前**最後一次**有效提交的 Private 評測分數為準，不是取最高分。
- 審查：指定隊伍須提交程式碼與技術文件，最終名次依 Private 成績與審查結果確認。實際時程以主辦單位正式公告為準。

**Q22. 排行榜看得到各成因類別的分數嗎？**
看不到。排行榜明細只有 `F1_TIoU`、`F1_TEXT`、`TIoU_solar_panel`、`TIoU_hotspot`、`TIoU_crack` 五個欄位（第 8 節），不顯示各成因類別的明細。

**Q23. 成因類別與參考描述會公開嗎？**
不會。成因類別的名稱、數量與參考描述都不公開（第 7.1 節）；測試集的標準答案也不公開（第 2 節）。

**Q24. 為什麼我依本文件試算的文字分數和排行榜不同？**
主要原因是正式評分使用的成因類別與參考描述不公開，自行試算時只能用自己決定的分法與參考描述（第 10.3 節）。其他可能的原因：
- 影像不同：自行驗證用的是自己切出的驗證集，排行榜則是在 Public 或 Private 的影像清單上計算（第 8 節）。
- 彙整方式：F1_TEXT 是對整個 subset 的各成因類別先平均、再取調和平均、最後換算（第 7.5 節），單一句子的 s 不能直接當成 F1_TEXT。
- 四捨五入：排行榜明細四捨五入到小數點後 6 位（第 8 節）。
- 執行環境：不同的硬體、套件版本或批次組合，可能讓 s 在小數點後第 6 位以後有極小的差異（第 7.3 節）。
- 設定不同：模型、層數、語言或 rescale 的設定與第 7.3 節不同時，結果也會不同。

排行榜分數以平台評分程式的計算結果為準。

評分程式沒有任何變更，排行榜上既有的分數維持不變，不會重新計算（第 1 節）。本文件描述的就是平台現行評分程式的計算方式。

**Q27. BERTScore 有沒有門檻？有沒有 rescale？負值會被截成 0 嗎？**
單句分數 s 沒有門檻；有 rescale；負值不會被截成 0。
- s 是以 `bert_score` 內建的 `bert-base-chinese` 中文 baseline rescale 後的 BERTScore F1（第 7.3 節）。相似度低於 baseline 時 s 是負值，負值原樣計入該成因類別的平均（第 7.2 節）。
- 換算只在最後對 raw 做一次：raw ≤ 0.30 時 F1_TEXT = 0，raw ≥ 0.70 時為 1，中間線性換算。任一成因類別的平均 s ≤ 0 時，raw = 0（第 7.5 節）。
- 配對另有 IoU ≥ 0.5 的條件（第 6 節），與 BERTScore 無關。

**Q28. 根因文字只對配對成功的 GT 計分嗎？沒有配對到的框和 GT 怎麼算？**
是，只有配對成功的 GT 會計算單句分數 s。
- 沒有配對成功的框：它的 `reason` 不會被計分，不影響 F1_TEXT。框本身仍計入定位分數（第 5、6 節）。
- 沒有配對成功的 GT：沒有 s，不計入所屬成因類別的平均，不是記 0（第 7.2 節）。但只要某個成因類別在該 subset 中完全沒有配對成功的 GT，F1_TEXT 就是 0（第 7.5 節）。
- 配對成功但 `reason` 空白：s = 0，計入該成因類別的平均（第 7.2 節）。
